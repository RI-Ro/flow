# Техническое задание на доработку «Флоу»

Документ фиксирует текущее состояние, разбирает каждую заявленную
проблему до причины и описывает объём работ. Часть дефектов уже
исправлена в этой поставке — они помечены как **[исправлено]** и
требуют только проверки на вашей стороне.

---

## 1. Цель

Kanban-планировщик с проектами, задачами, обсуждением, файлами и
разграничением доступа. Требование, определяющее архитектуру:
**изменения одного пользователя должны немедленно появляться у всех
остальных, кому эта задача или проект доступны** — на доске, в карточке
задачи и во «Входящих», с соблюдением тех же правил доступа, что и в
обычных запросах.

Стек: React (Vite) + Go (Fiber) + PostgreSQL с RLS + JWT + WebSocket.
Расчётная нагрузка — от 300 одновременных пользователей.

---

## 2. Текущее состояние

Реализовано и проверено сверкой исходников: аутентификация с ротацией
refresh-токенов, RLS-политики на всех таблицах, панель администратора
(создание, правка, роли, блокировка, сброс пароля, мягкое удаление),
WebSocket-хаб с вычислением получателей на стороне БД, точечные
обновления состояния на фронте вместо перезагрузки доски.

Не проверено выполнением: в среде, где собиралась эта поставка, нет ни
Go, ни доступа в интернет для загрузки зависимостей, поэтому код
сверялся построчно, но не компилировался и не запускался. Это главный
источник риска и причина, по которой дефекты ниже дошли до вас.

## 3. Разбор заявленных проблем

### 3.1. Синхронизация не работает вообще — **[исправлено]**

**Причина найдена и устранена.** В `frontend/vite.config.js` правила
прокси были заданы так:

```js
proxy: {
  "/api": { target: "http://localhost:8080" },   // перехватывал всё
}
```

Vite выбирает **первое совпадение по префиксу**. Правило `/api`
перехватывало и `/api/ws`, отправляя запрос в обычный http-прокси, где
апгрейд соединения не выполняется. WebSocket не поднимался никогда —
без единой ошибки в консоли, просто «ничего не происходит». Это
объясняет, почему не работала вся интерактивность разом: и задачи, и
комментарии, и уведомления.

Исправление: правило `/api/ws` с `ws: true` объявлено первым.

**Что проверить у себя:** после `npm run dev` в правом верхнем углу
рядом с колокольчиком есть индикатор — зелёная точка означает живое
соединение, серая — переподключение. Либо напрямую:

```bash
websocat "ws://localhost:8080/api/ws?access_token=$TOKEN"
```

**Что доработать (объём: 1–2 дня).** Каркас рассылки готов: события
`task`, `step`, `comment`, `attachment`, `columns`, `board`,
`notification` публикуются после каждой мутации, получателей считают
SQL-функции `app.board_watchers` / `app.task_watchers`, зеркалящие
условия RLS. После восстановления соединения требуется:

- сквозная проверка каждого типа события двумя браузерами;
- **дозагрузка состояния после переподключения.** Сейчас при обрыве
  события теряются безвозвратно: клиент переподключается, но пропущенное
  не догоняет. Нужен запрос актуального состояния доски при событии
  `connected`, иначе после недолгой потери сети экран остаётся
  устаревшим до ручного обновления страницы.

### 3.2. Ошибки в `0003_seed.sql` — **[исправлено]**

**Обе найдены, причина ровно та, на которую вы указали.** Конструкция
была такой:

```sql
FROM app.boards b
JOIN app.columns c ON c.board_id = b.id AND c.position = t.col   -- t ещё не объявлен
CROSS JOIN (VALUES ...) AS t(title, descr, prio, due, col, pos, tags)
```

Ссылка на псевдоним `t` в условии соединения раньше, чем он введён в
`FROM`, недопустима — PostgreSQL отвечает `invalid reference to
FROM-clause entry for table "t"`. Два вхождения, по одному на каждый
демо-проект. `JOIN` перенесён после `CROSS JOIN`.

### 3.3. Не подходят пароли демо-пользователей — **[исправлено]**

Две наложившиеся причины:

1. Ранняя версия seed содержала bcrypt-хеш, вписанный строкой и не
   проверенный вычислением — он не соответствовал `DemoPassword1!`.
   Сейчас хеш считается прямо в базе через `crypt()` из pgcrypto.
2. `ON CONFLICT (email) DO NOTHING` означал, что на базе, где seed
   однажды отработал со старым хешем, повторный запуск ничего не
   исправлял. Заменено на `DO UPDATE SET password_hash = EXCLUDED.
   password_hash`.

**Что сделать у себя:**

```bash
psql "$DATABASE_URL" -f backend/migrations/0003_seed.sql
```

Либо, если демо-данные не нужны, задать пароль напрямую:

```sql
UPDATE app.users SET password_hash = crypt('ВашПароль', gen_salt('bf', 12))
 WHERE email = 'anna@team.dev';
```

Учтите: из-за 3.2 seed прерывался на вставке задач, поэтому в базе,
скорее всего, есть пользователи, но нет ни задач, ни грантов, ни
комментариев. После исправления seed отработает целиком.

### 3.4. Разные списки «моей команды» у владельца и редактора — **[исправлено]**

**Это была тихая потеря данных, а не только неудобство.** Форма задачи
отправляет полный список исполнителей, а обработчик `replaceAssignees`
удаляет всех и вставляет присланных заново. При этом список кандидатов в
форме строился **только из личной команды текущего пользователя**. В
результате редактор, открыв задачу, физически не видел исполнителей,
назначенных владельцем из другой команды, — и они не попадали в
отправляемый список, то есть снимались с задачи при первом же
сохранении, без какого-либо действия со стороны редактора.

Исправление: кандидаты теперь — объединение личной команды, участников
проекта и уже назначенных исполнителей. Назначенные не из своей команды
помечены точкой и подписью, чтобы снятие было осознанным.

**Что доработать (объём: 1 день).** Полное решение требует перехода от
«прислали список целиком» к явным операциям добавления и снятия:

```
POST   /api/tasks/:id/assignees      { userId }
DELETE /api/tasks/:id/assignees/:uid
```

Тогда конкурентная правка двумя редакторами перестанет затирать чужие
изменения в принципе — сейчас последний сохранивший всё ещё выигрывает.

### 3.5. Чек-лист не работает — **требуется диагностика**

Обработчики разделены на два маршрута, что убрало прежнюю
неоднозначность:

- `POST /api/tasks/:taskID/steps/:stepID/toggle` — отметка выполнения,
  доступна любому участнику с правом `contribute`;
- `PATCH /api/tasks/:taskID/steps/:stepID` — правка текста, только
  редактор задачи.

Маршруты, клиентские вызовы и RLS-политики сверены между собой и
согласованы. Назвать причину, не запустив систему, я не могу — и не
буду гадать. **Прошу прислать диагностику:**

```bash
# в консоли браузера при клике по чекбоксу — вкладка Network:
# какой запрос уходит, какой код ответа и какое тело ответа

# либо напрямую:
curl -i -X POST "http://localhost:8080/api/tasks/$TASK/steps/$STEP/toggle" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"done":true}'
```

Наиболее вероятные кандидаты, которые проверятся этим запросом:
`404` — задача не видна под RLS; `403` — не хватает уровня доступа;
`400` — расхождение в формате тела; `500` — ошибка в SQL.

Отдельно: до исправления 3.2 в базе **не было ни одной задачи с
чек-листом**, потому что seed прерывался. Возможно, дефект исчезнет сам
после полного применения seed.

### 3.6. Не работает установка своей картинки фоном — **требуется диагностика**

Цепочка сверена: загрузка (`POST /boards/:id/background`) сохраняет файл,
пишет `bg_file_id` и ставит `bg_preset = 'custom'`; отдача
(`GET /boards/:id/background`) проверяет доступ политикой `files_select`;
middleware аутентификации принимает токен из query-параметра, потому что
`<img src>` не может выставить заголовок. Явного разрыва в этой цепочке
я не нашёл.

**Прошу уточнить, на каком шаге останавливается:** загрузка не
проходит (какой код ответа), картинка загрузилась, но не отображается
(что показывает Network для запроса `/background`), или отображается в
предпросмотре настроек, но не на доске.

Известное узкое место, которое стоит устранить независимо от результата:
права на смену фона проверяются политикой `boards_update`, разрешающей
правку **только владельцу** проекта. Редактор, открывший настройки,
получит отказ — интерфейс при этом кнопку не прячет. Нужно либо скрыть
раздел фона у редактора, либо расширить политику.

### 3.7. Часть запросов остаётся медленной — **требуется профилирование**

Сделано: индексы под конкретные запросы (`0001_schema.sql`,
`0005_admin.sql`), устранение N+1 при подгрузке шагов и грантов,
триграммный индекс для поиска по справочнику, пул соединений на 40.

Дальше нужны факты, а не догадки — какой именно запрос медленный.
**Прошу включить лог медленных запросов и прислать выдержку:**

```sql

-- поработать в интерфейсе, затем посмотреть лог PostgreSQL
```

Плюс лог самого API: в нём есть длительность каждого запроса
(`${latency}` в формате логгера) и адрес — этого достаточно, чтобы
понять, тормозит база или обработчик.

Заранее видимые кандидаты, требующие работы:

| Место | Проблема | Решение |
|---|---|---|
| `GET /boards/:id/tasks` | Отдаёт все задачи доски разом со счётчиками комментариев и вложений подзапросами на каждую строку | Пагинация по колонкам либо материализованные счётчики, обновляемые триггером |

## 4. Приёмка

Работа считается выполненной, когда воспроизводятся все сценарии:

1. **Синхронизация.** Два браузера, разные пользователи, одна доска.
   Перенос задачи, правка, комментарий, файл, отметка в чек-листе,
   изменение колонок — каждое действие видно во втором браузере без
   обновления страницы, за время до секунды.
2. **Синхронизация во «Входящих».** Пользователь с точечным грантом
   видит изменения задачи, не имея доступа к остальной доске.
3. **Разграничение при рассылке.** Пользователь, не имеющий доступа к
   задаче, не получает по ней событий — проверяется подключением
   `websocat` под его токеном во время чужой работы.
4. **Восстановление после обрыва.** Отключить сеть на 30 секунд,
   включить: состояние догоняется автоматически.
5. **Исполнители.** Владелец назначает исполнителя не из команды
   редактора; редактор сохраняет задачу — исполнитель остаётся.
6. **Чек-лист.** Отметка любым участником с правом участия, правка
   текста — только редактором.
7. **Демо-данные.** `make migrate && make seed` проходит без ошибок,
   вход под `anna@team.dev` / `DemoPassword1!` работает.
8. **Фон.** Загрузка своего изображения, отображение на доске,
   размытие.
9. **Производительность.** Под нагрузкой 300 сессий 95-й процентиль
   ответа REST — до 200 мс, доставка события — до 1 секунды.

## 5. Риски

- **Главный: код не проверялся выполнением.** Пока не будет прогона
  `go build` и запуска с реальной базой, любая правка может содержать
  дефект того же рода, что 3.2. Первое, что стоит сделать, — собрать и
  запустить, а не читать код.
- Хаб WebSocket держит соединения в памяти процесса: при
  масштабировании на несколько экземпляров API потребуется внешний
  pub/sub (Redis или `LISTEN/NOTIFY`).
- Файлы лежат на локальном диске — то же ограничение.
- Окно до 15 минут, в течение которого заблокированный пользователь
  работает по уже выданному access-токену. Сокращается уменьшением
  `ACCESS_TTL` ценой более частого обновления.
