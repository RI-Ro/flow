# Сборка и запуск на одном адресе

Цель: приложение целиком (интерфейс, API, WebSocket, файлы) доступно по
одному адресу вида `http://192.168.1.50:8080` — без отдельного веб-сервера,
без второго порта для фронтенда и без настройки CORS.

Это достигается тем, что Go-сервер сам раздаёт собранный фронтенд.
Тогда браузер обращается к API и к WebSocket по тому же адресу, откуда
загрузил страницу, — правила ограничения источников не задействуются
в принципе.

---

## Что нужно установить

| Компонент | Версия | Зачем |
|---|---|---|
| Go | 1.22+ | сборка сервера |
| Node.js | 18+ | сборка фронтенда (только на время сборки) |
| PostgreSQL | 14+ | база |

На машине, где приложение будет работать постоянно, Node.js не нужен:
собрать можно где угодно и скопировать результат.

---

## Шаг 1. База данных

Миграции выполняются **владельцем таблиц** (обычно `postgres`), а не
строкой подключения приложения: у роли `app_user` намеренно нет прав
менять политики доступа.

```bash
sudo -u postgres createdb kanban

cd backend/migrations
for f in 0000_roles.sql 0001_schema.sql 0002_rls.sql \
         0004_fix_auth.sql 0005_admin.sql 0006_task_color.sql; do
    sudo -u postgres psql -d kanban -v ON_ERROR_STOP=1 -f "$f" || break
done

# Демонстрационные данные — по желанию
sudo -u postgres psql -d kanban -v ON_ERROR_STOP=1 -f 0003_seed.sql

# Право подключаться к этой базе: в 0000_roles.sql его выдать нельзя,
# потому что базы там ещё может не существовать.
sudo -u postgres psql -d kanban -c \
  "GRANT CONNECT ON DATABASE kanban TO app_user, app_owner;"
```

Смените пароли ролей, заданные в `0000_roles.sql` заглушками:

```bash
sudo -u postgres psql -c "ALTER ROLE app_user PASSWORD 'ваш_пароль';"
```

## Шаг 2. Сборка

```bash
make build
```

Одна команда делает три вещи: собирает бинарник в `bin/api`, собирает
фронтенд и кладёт статику в `bin/web`. Вручную то же самое:

```bash
cd backend && go mod tidy && go build -o ../bin/api ./cmd/api
cd ../frontend && npm install && npm run build
cd .. && rm -rf bin/web && cp -r frontend/dist bin/web
```

`go mod tidy` требует доступа в интернет — он скачивает зависимости и
создаёт `go.sum`. Это единственный шаг, которому нужна сеть.

## Шаг 3. Запуск

```bash
cd bin

export DATABASE_URL='postgres://app_user:ваш_пароль@localhost:5432/kanban?sslmode=disable'
export JWT_SECRET="$(openssl rand -base64 48)"
export STATIC_DIR=./web
export APP_ADDR=:8080
export UPLOAD_DIR=./uploads
export APP_ENV=production

./api
```

Приложение доступно по адресу машины: `http://192.168.1.50:8080`.

Почему всё работает по одному адресу:

- `APP_ADDR=:8080` — без указания хоста сервер слушает **все** сетевые
  интерфейсы. Если написать `127.0.0.1:8080`, снаружи он будет
  недоступен.
- `STATIC_DIR=./web` — включает раздачу интерфейса. Любой неизвестный
  адрес отдаёт `index.html`, поэтому ссылки вида `/b/<uuid>` открываются
  напрямую и переживают обновление страницы.
- WebSocket подключается к тому же хосту и порту, откуда загружена
  страница, — отдельная настройка не нужна.
- `ALLOWED_ORIGINS` при такой схеме не используется: источник один.

**`JWT_SECRET` обязательно задать явно.** Без него в режиме разработки
генерируется случайный ключ на каждый запуск, и все сессии сбрасываются
при перезапуске; в `APP_ENV=production` сервер откажется стартовать.

## Шаг 4. Первый вход

Если применяли `0003_seed.sql` — `anna@team.dev` / `DemoPassword1!`,
она же администратор.

Если база пустая — откройте адрес приложения и зарегистрируйтесь.
**Первая учётная запись в пустой базе создаётся всегда и сразу получает
права администратора**, даже когда самостоятельная регистрация
отключена. Дальше пользователей заводит администратор: аватар в правом
верхнем углу → «Пользователи».

Чтобы разрешить всем регистрироваться самостоятельно:

```bash
export ALLOW_SELF_REGISTRATION=true
```

## Доступ по сети

Открыть порт:

```bash
# Ubuntu / Debian
sudo ufw allow 8080/tcp

# RHEL / CentOS / Fedora
sudo firewall-cmd --permanent --add-port=8080/tcp && sudo firewall-cmd --reload
```

Проверить, что сервер действительно слушает все интерфейсы:

```bash
ss -tlnp | grep 8080     # должно быть *:8080 или 0.0.0.0:8080, не 127.0.0.1:8080
curl -s http://localhost:8080/healthz
```

Ответ `/healthz` показывает состояние: число открытых WebSocket-соединений
и занятость пула соединений с базой.

## Постоянная работа: systemd

`/etc/systemd/system/kanban.service`:

```ini
[Unit]
Description=Флоу — планирование задач
After=network.target postgresql.service

[Service]
Type=simple
User=kanban
WorkingDirectory=/opt/kanban
ExecStart=/opt/kanban/api

Environment=APP_ENV=production
Environment=APP_ADDR=:8080
Environment=STATIC_DIR=/opt/kanban/web
Environment=UPLOAD_DIR=/opt/kanban/uploads
# Секреты — отдельным файлом с правами 600, а не в этом юните:
# его содержимое видно любому пользователю системы через systemctl cat.
EnvironmentFile=/etc/kanban/secrets.env

Restart=always
RestartSec=5

# Ограничения: сервису нужен доступ только к своему каталогу
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/kanban/uploads

[Install]
WantedBy=multi-user.target
```

`/etc/kanban/secrets.env` (права `chmod 600`):

```
DATABASE_URL=postgres://app_user:пароль@localhost:5432/kanban?sslmode=disable
JWT_SECRET=сгенерированный_ключ
```

```bash
sudo useradd -r -s /usr/sbin/nologin kanban
sudo mkdir -p /opt/kanban/uploads && sudo chown -R kanban /opt/kanban
sudo cp bin/api /opt/kanban/ && sudo cp -r bin/web /opt/kanban/

sudo systemctl daemon-reload
sudo systemctl enable --now kanban
sudo journalctl -u kanban -f
```

## Через Docker

`docker-compose.yml` в поставке поднимает базу и API, но фронтенд там
собирается отдельно. Чтобы получить ту же схему «всё по одному адресу»,
соберите статику и смонтируйте её:

```bash
cd frontend && npm install && npm run build && cd ..

docker compose up -d db
docker compose run --rm -v "$PWD/frontend/dist:/web" \
  -e STATIC_DIR=/web -p 8080:8080 api
```

Либо добавьте в `Dockerfile` этап сборки фронтенда — тогда образ будет
самодостаточным.

## HTTPS

Приложение работает по HTTP. Для внешнего доступа поставьте перед ним
обратный прокси — тогда WebSocket тоже пойдёт через него:

```nginx
server {
    listen 443 ssl;
    server_name kanban.example.com;

    ssl_certificate     /etc/letsencrypt/live/kanban.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/kanban.example.com/privkey.pem;

    client_max_body_size 30m;   # не меньше MAX_UPLOAD_MB

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Без этих трёх строк WebSocket не поднимется, и синхронизация
        # между пользователями работать не будет.
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # Соединение WebSocket долгоживущее: стандартные 60 секунд
        # заставляли бы клиента переподключаться каждую минуту.
        proxy_read_timeout 3600s;
    }
}
```

При работе через прокси сервер за ним остаётся на `127.0.0.1:8080` —
наружу его открывать не нужно.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | `postgres://app_user:change_me_user@localhost:5432/kanban?sslmode=disable` | подключение к базе; в production обязательна |
| `JWT_SECRET` | случайный при каждом запуске | подпись токенов; в production обязательна |
| `APP_ADDR` | `:8080` | адрес и порт |
| `STATIC_DIR` | пусто | каталог с интерфейсом; пусто — API без интерфейса |
| `APP_ENV` | `development` | `production` включает строгие проверки и скрывает подробности ошибок |
| `UPLOAD_DIR` | `./var/uploads` | каталог вложений и фонов |
| `MAX_UPLOAD_MB` | `25` | предел размера файла |
| `ACCESS_TTL` | `15m` | срок действия access-токена |
| `REFRESH_TTL` | `720h` | срок сессии |
| `DB_POOL_SIZE` | `40` | соединений с базой |
| `RATE_LIMIT_PER_MIN` | `600` | запросов в минуту с адреса |
| `ALLOW_SELF_REGISTRATION` | `false` | самостоятельная регистрация |

## Если что-то не работает

**Страница открывается, но пусто или 404 при обновлении на `/b/<uuid>`** —
не задан `STATIC_DIR` либо в нём нет `index.html`. Проверьте `ls $STATIC_DIR`.

**Интерфейс есть, но данные не грузятся** — откройте `/healthz`. Если он
не отвечает, сервер не запустился; если отвечает, смотрите вкладку
Network: запросы к `/api/...` должны идти на тот же адрес.

**Нет синхронизации между пользователями** — в интерфейсе рядом с
колокольчиком есть индикатор: зелёная точка означает живое соединение.
Если серая, смотрите Network → WS. За обратным прокси почти всегда
причина в отсутствии заголовков `Upgrade`/`Connection` (см. раздел про
nginx).

**Не открывается с другой машины** — сервер слушает только localhost
(проверьте `ss -tlnp`) или закрыт порт в межсетевом экране.
