# Несколько экземпляров через systemd

Задача: на одной машине работает несколько независимых установок — под
разными именами, со своими базами, портами и ключами. Файлы для этого
лежат в `deploy/`.

---

## 1. Подготовка

```bash
sudo useradd -r -s /usr/sbin/nologin kanban

# Бинарник и статика — общие для всех экземпляров: код одинаковый.
sudo install -d -o root -g kanban -m 750 /opt/kanban/bin
sudo install -o root -g kanban -m 755 bin/api /opt/kanban/bin/api
sudo cp -r bin/web /opt/kanban/web

# У каждого экземпляра свой рабочий каталог и свои вложения.
for name in alpha beta gamma; do
    sudo install -d -o kanban -g kanban -m 750 /opt/kanban/$name/uploads
done

# Файлы окружения — доступны только root и группе сервиса.
sudo install -d -o root -g kanban -m 750 /etc/kanban
```

## 2. Файл окружения на каждый экземпляр

```bash
sudo cp deploy/instance.env.example /etc/kanban/alpha.env
sudo chown root:kanban /etc/kanban/alpha.env
sudo chmod 600 /etc/kanban/alpha.env
sudo nano /etc/kanban/alpha.env
```

Что обязательно различается между экземплярами:

| Переменная | Почему нельзя делать общей |
|---|---|
| `APP_ADDR` | два процесса не займут один порт |
| `DATABASE_URL` | общая база означала бы общих пользователей и проекты |
| `JWT_SECRET` | при общем ключе токен, выданный одним сайтом, приняли бы на другом |
| `UPLOAD_DIR` | вложения разных установок смешались бы в одном каталоге |

`STATIC_DIR` наоборот стоит держать общим — интерфейс одинаковый.

Ключ для каждого:

```bash
openssl rand -base64 48
```

## 3. Базы данных

Отдельная база и отдельный владелец на каждый экземпляр:

```bash
for name in alpha beta gamma; do
    sudo -u postgres createdb kanban_$name
    for f in 0000_roles 0001_schema 0002_rls 0004_fix_auth \
             0005_admin 0006_task_color 0007_activity_notify; do
        sudo -u postgres psql -d kanban_$name -v ON_ERROR_STOP=1 \
            -f backend/migrations/$f.sql || break
    done
    sudo -u postgres psql -d kanban_$name -c \
        "GRANT CONNECT ON DATABASE kanban_$name TO app_user, app_owner;"
done
```

Роли `app_user` и `app_owner` создаются один раз на кластер — они общие,
а вот права на подключение выдаются к каждой базе отдельно. Если нужна
полная изоляция и по ролям, создайте `app_user_alpha` и подставьте их в
`DATABASE_URL`.

Проверьте `max_connections`: суммарный `DB_POOL_SIZE` всех экземпляров
плюс запас на обслуживание не должен его превышать.

```bash
sudo -u postgres psql -c "SHOW max_connections;"
```

## 4. Установка юнита

```bash
sudo cp deploy/kanban@.service /etc/systemd/system/
sudo systemctl daemon-reload

sudo systemctl enable --now kanban@alpha
sudo systemctl enable --now kanban@beta
sudo systemctl enable --now kanban@gamma
```

Знак `@` делает юнит шаблоном: `%i` внутри подставляется из имени после
`@`. Один файл обслуживает любое число экземпляров, каждый читает свой
`/etc/kanban/<имя>.env`.

Управление:

```bash
systemctl status kanban@alpha
journalctl -u kanban@alpha -f
systemctl restart kanban@beta

# все сразу
systemctl restart 'kanban@*'
```

## 5. Проверка

```bash
for p in 8081 8082 8083; do
    echo -n "$p: "; curl -s http://127.0.0.1:$p/healthz
done
```

# Нужен ли nginx или haproxy?

Разделю два вопроса, которые часто смешивают.

## Для производительности — нет

Обратный прокси не ускорит это приложение. Go обслуживает HTTP сам,
здесь используется fasthttp, и на нагрузке в несколько сотен
одновременных пользователей узкое место — не HTTP-слой, а база данных.
Добавление nginx перед Go на такой нагрузке скорее добавит небольшую
задержку, чем уберёт.

Если запросы медленные, смотреть надо в другую сторону:

```sql
ALTER SYSTEM SET log_min_duration_statement = '200ms';
SELECT pg_reload_conf();
```

и в лог приложения — там есть длительность каждого запроса. Прокси в
этом не поможет.

## Для нескольких имён на одном порту — да, обязательно

Порт 443 на машине один, а имён несколько. Разобрать, какому экземпляру
адресован запрос, по имени из заголовка `Host` может только прокси —
само приложение слушает свой порт и про соседей не знает.

Прокси нужен ещё и для того, что приложение сознательно не делает:

- **TLS.** Сертификаты, их продление, современные наборы шифров.
  Держать это в приложении — значит перезапускать его при каждом
  обновлении сертификата.
- **Ограничение размера запроса на границе.** `client_max_body_size`
  отсекает слишком большой файл до того, как он дойдёт до приложения.
- **Единая точка для журналов доступа и правил на уровне сети.**

Что выбрать: для описанной задачи достаточно **nginx** —
`deploy/nginx-kanban.conf`. Он же отдаёт статику и терминирует TLS.
**haproxy** (`deploy/haproxy-kanban.cfg`) имеет смысл, если понадобятся
развитые проверки работоспособности и вывод экземпляра из обслуживания
без разрыва текущих соединений.

## Что критично не забыть в конфигурации прокси

Три строки, без которых WebSocket не поднимется:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection $connection_upgrade;
```

Симптом при их отсутствии коварный: сайт открывается и работает, но
изменения одного пользователя не появляются у других — события просто
никуда не идут. Это выглядит как ошибка в приложении, хотя причина в
прокси.

И ещё одно, не столь очевидное: приложению нужно сказать, что прокси
можно доверять.

```
TRUSTED_PROXIES=127.0.0.1,::1
```

Без этого приложение видит в каждом запросе адрес прокси, а не клиента,
и ограничение частоты (`RATE_LIMIT_PER_MIN`) становится общим на всех
пользователей сразу — один активный сотрудник исчерпает лимит за
остальных. Доверять заголовку можно только от заданных адресов: иначе
его подделает любой клиент и обойдёт ограничение вовсе.

И таймаут: соединение WebSocket живёт часами и большую часть времени
молчит. Стандартные 60 секунд обрывали бы его каждую минуту.

```nginx
proxy_read_timeout 3600s;
```

В haproxy тому же служит `timeout tunnel 1h`.

# Почему нельзя размножать один сайт

Соблазнительно поставить два экземпляра на одну базу и распределить
между ними нагрузку. С этим приложением так делать нельзя.

WebSocket-хаб (`internal/realtime`) держит открытые соединения в памяти
своего процесса. Если Пётр подключён к экземпляру №1, а Мария к №2, то
изменение, сделанное Марией, обработает второй процесс — и разошлёт
событие только тем, кто подключён к нему. Пётр не увидит ничего до
перезагрузки страницы. Причём поведение будет плавающим: иногда
синхронизация работает (оба попали на один экземпляр), иногда нет.

Описанная выше схема безопасна именно потому, что каждый экземпляр — это
отдельный сайт со своей базой, а не копия одного и того же.

Чтобы масштабировать один сайт горизонтально, рассылку нужно вынести из
памяти процесса во внешнюю шину — Redis Pub/Sub либо `LISTEN/NOTIFY`
самого PostgreSQL. Место для этого одно: `Hub.SendTo` вместо прямой
записи в сокеты публикует сообщение в шину, а каждый экземпляр слушает
её и доставляет своим подключениям. Работы примерно на день, но пока
нагрузка укладывается в один процесс, это лишняя деталь.

Ориентир по ёмкости одного экземпляра: несколько тысяч одновременных
WebSocket-соединений при `LimitNOFILE=65535`. Раньше упрётесь в базу.
