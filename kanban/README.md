# Флоу — планирование задач в реальном времени

Kanban-доска на Go (Fiber) + PostgreSQL с политиками RLS, JWT-аутентификацией
и WebSocket-синхронизацией между всеми пользователями, которым доступен
проект или задача. Фронтенд — React (Vite).

## Администрирование пользователей

Учётные записи управляются из панели: аватар в правом верхнем углу →
«Пользователи» (пункт видят только администраторы). Доступно создание,
правка, смена роли, блокировка, принудительная смена пароля, удаление
и восстановление.

Первым администратором миграция `0005_admin.sql` делает самую раннюю
существующую учётную запись — на демо-данных это `anna@team.dev`.
Назначить админа вручную:

```sql
UPDATE app.users SET role = 'admin' WHERE email = 'вы@example.com';
```

Что здесь важно с точки зрения надёжности:

- **Блокировка и удаление действуют немедленно.** Раньше `Refresh` не
  проверял состояние учётной записи, поэтому отключённый пользователь
  продолжал обновлять токен и работать до истечения refresh-срока —
  месяц. Теперь при обновлении токена проверяется `is_active` и
  `deleted_at`, все сессии гасятся через `app.revoke_user_sessions`,
  а открытые WebSocket-соединения принудительно обрываются
  (`Hub.Disconnect`). Остаётся окно до 15 минут по уже выданному
  access-токену — его нельзя отозвать по природе подписанных токенов,
  поэтому TTL и держится коротким.
- **Права администратора проверяются запросом к базе на каждый вызов**
  (`app.is_admin`), а не по полю в JWT: иначе снятие прав вступало бы в
  силу с задержкой в те же 15 минут.
- **Удаление мягкое.** `created_by` в проектах, задачах, комментариях и
  файлах объявлены `ON DELETE RESTRICT`: физическое удаление строки либо
  было бы отвергнуто базой, либо уничтожило бы историю работы. Поэтому
  учётная запись помечается удалённой, снимаются членства в командах и
  точечные гранты, а имя продолжает отображаться в старых задачах
  зачёркнутым. Восстановление возвращает вход, но не доступ к
  проектам — его заново выдаёт владелец проекта.
- **Последнего администратора нельзя разжаловать, заблокировать или
  удалить** (`app.other_admins_count`), иначе системой стало бы
  некому управлять. Себя удалить или заблокировать тоже нельзя.
- **Роль в системе и роль на доске — разные вещи.** `admin` управляет
  учётными записями; он не получает автоматически доступ к содержимому
  чужих проектов — политики RLS для досок и задач на него не делают
  исключений.

## Регистрация закрыта по умолчанию

Раз учётными записями управляет администратор, открытая форма
регистрации означала бы, что завести себе доступ может любой, кто
дотянулся до адреса сервера. Поэтому `/api/auth/register` по умолчанию
отвечает отказом.

Два исключения, оба намеренные:

- **Совершенно пустая база.** Первая регистрация разрешена всегда и
  сразу выдаёт права администратора — иначе после установки войти было
  бы некому и первого админа пришлось бы заводить руками в psql.
- **Явное разрешение.** `ALLOW_SELF_REGISTRATION=true` в окружении
  возвращает открытую регистрацию, если она нужна.

## Известная проблема в ранних версиях (уже исправлена в этой поставке)

Если у вас уже поднята база по более ранней версии этого проекта и
вход/регистрация падают с «Недостаточно прав» — это была реальная
ошибка в `0002_rls.sql`: RLS была включена на `app.users` и
`app.refresh_tokens`, но политика `INSERT` для `app.users` отсутствовала
вовсе, а политика на `app.refresh_tokens` не учитывала, что вход и
регистрация выполняются ДО появления `app.user_id` в транзакции — по
умолчанию Postgres запрещает операцию, для которой нет ни одной
подходящей политики. Заодно demo-пароль в `0003_seed.sql` был вписан
как непроверенная строка, не как настоящий bcrypt-хеш `DemoPassword1!`.

Если база уже создана — примените точечный патч, ничего пересоздавать
не нужно:

```bash
make fix-auth
```

На свежей установке (`make migrate && make seed` из файлов этой
поставки) патч не нужен — `0002_rls.sql` и `0003_seed.sql` уже
исправлены.

## Запуск без Docker (подробно)

Нужны: PostgreSQL 14+, Go 1.22+, Node.js 18+.

```bash
# 1. База данных
createdb kanban
psql kanban -v ON_ERROR_STOP=1 -f backend/migrations/0000_roles.sql
psql kanban -v ON_ERROR_STOP=1 -f backend/migrations/0001_schema.sql
psql kanban -v ON_ERROR_STOP=1 -f backend/migrations/0002_rls.sql
# демо-данные (необязательно, но нужны для входа тестовыми учётками)
psql kanban -v ON_ERROR_STOP=1 -f backend/migrations/0003_seed.sql

# Ролям из 0000_roles.sql нужно право подключаться именно к этой базе —
# оно не выдаётся автоматически, потому что база на момент выполнения
# 0000 могла ещё не существовать:
psql kanban -c "GRANT CONNECT ON DATABASE kanban TO app_user, app_owner;"

# 2. Бэкенд
cd backend
cp ../.env.example .env
# откройте .env и задайте JWT_SECRET:
#   openssl rand -base64 48
export $(grep -v '^#' .env | xargs)   # или используйте direnv/dotenv
go mod tidy      # скачает зависимости и создаст go.sum — нужен интернет
go run ./cmd/api
# сервер поднимется на :8080, лог в JSON в stdout

# 3. Фронтенд (в отдельном терминале)
cd frontend
npm install
npm run dev
# откройте http://localhost:5173
```

Проверить, что бэкенд жив и сколько сейчас открыто WebSocket-соединений
и соединений с базой:

```bash
curl -s http://localhost:8080/healthz | jq
```

Проверить WebSocket-подключение вручную (потребуется `websocat` или `wscat`):

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"anna@team.dev","password":"DemoPassword1!"}' | jq -r .accessToken)

websocat "ws://localhost:8080/api/ws?access_token=$TOKEN"
# откройте задачу в интерфейсе, поставьте отметку в чек-листе —
# в этом терминале появится JSON-событие {"type":"step",...}
```

Проверить политики RLS отдельно (без запуска API):

```bash
make test
```

Демо-учётные записи (после `make seed` / применения `0003_seed.sql`):
`anna@team.dev` … `alexey@team.dev`, пароль у всех `DemoPassword1!`.
Анна — владелец «Мобильного приложения», а в проекте «Инфраструктура API»
ей открыты точечно две задачи (не весь проект) — они появятся в разделе
«Входящие» вместе с именем того, кто их поставил.

## Многопоточность и Fiber

Fiber запущен **без Prefork**. Это осознанное решение, а не недосмотр:
Prefork поднимает несколько независимых ОС-процессов с раздельной
памятью каждый, а WebSocket-хаб (`internal/realtime`) и пул соединений
с базой — структуры в памяти одного процесса. С Prefork клиент,
подключённый к воркеру №2, не узнал бы о событии, обработанном
воркером №1 — межпроцессный pub/sub (например, через `LISTEN/NOTIFY`
в Postgres или Redis) в проекте не реализован, и с Prefork рассылка
просто перестала бы доходить до части подключений.

Многопоточность здесь обеспечивает не форк процессов, а горутины:
транспорт Fiber (fasthttp) обслуживает каждое HTTP-соединение и каждое
WebSocket-соединение в своей горутине, и стандартный планировщик Go
распределяет их по всем ядрам процессора (`GOMAXPROCS`) сам. Такой
модели с запасом хватает на нагрузку кратно выше 300 одновременных
пользователей на одной машине среднего размера — узкое место при таких
числах почти всегда база данных, а не HTTP-слой, поэтому основное
внимание уделено пулу соединений и индексам (см. ниже), а не количеству
процессов Go.

Если понадобится горизонтальное масштабирование на несколько
экземпляров API за балансировщиком — WebSocket-рассылку придётся
вынести во внешний pub/sub (Redis Pub/Sub или `LISTEN/NOTIFY`), потому
что `Hub` в текущем виде держит подключения только в памяти своего
процесса. Это заложено как понятная точка расширения, но не реализовано
в этой версии, так как 300 пользователей одна инстанция обслуживает
без такого усложнения.

## Производительность на 300+ одновременных пользователей

- **Пул соединений с БД** (`DB_POOL_SIZE`, по умолчанию 40) рассчитан не
  на «одно соединение на пользователя», а на то, что каждый REST-запрос
  занимает соединение только на время своей транзакции — единицы
  миллисекунд при правильных индексах. 40 соединений с большим запасом
  обслуживают 300 параллельных пользователей, которые не шлют запросы
  буквально в одну и ту же миллисекунду.
- **Индексы под конкретные запросы**, а не «на всякий случай» — каждый
  прокомментирован в `migrations/0001_schema.sql` рядом с запросом,
  который он ускоряет: подсчёт комментариев/вложений на карточку без
  N+1, роль на доске, пагинация уведомлений, список задач колонки.
- **Без похода за всем проектом на каждую мелкую правку.** Раньше
  создание комментария или отметка в чек-листе перезапрашивали всю
  доску целиком — три запроса и полную перерисовку экрана. Теперь
  обработчик возвращает только изменённый объект, а WebSocket разносит
  его же остальным подключённым клиентам; полный список задач
  запрашивается один раз при открытии доски.
- **`MoveTask` рассылает всех, чья позиция сдвинулась**, а не только
  перетащенную карточку — при уплотнении нумерации в колонке соседние
  задачи тоже меняют `position`, и без этого у других участников они
  оставались бы в старом порядке до следующей полной перезагрузки.

## Реальное время (WebSocket)

- Один канал на вкладку: `GET /api/ws?access_token=...`. Токен идёт
  параметром запроса, а не заголовком `Authorization`, потому что
  браузерный конструктор `WebSocket` не позволяет выставить заголовки
  на рукопожатии.
- **Рассылка строго с учётом RLS.** Список получателей вычисляют не
  обработчики на Go, а SQL-функции `app.board_watchers(board_id)` и
  `app.task_watchers(task_id)` в `migrations/0002_rls.sql` — они
  зеркалят те же условия видимости, что и политики RLS для обычных
  REST-запросов. Хаб на стороне Go не содержит никакой логики прав
  вообще, только доставку уже готового списка `user_id`. Если модель
  доступа изменится, обе стороны (RLS-политики и watcher-функции)
  обязательно менять вместе — они специально оставлены в одном файле.
- **Поле `access` (и `myRole` для досок) в событии — это уровень
  доступа ОТПРАВИТЕЛЯ действия**, вычисленный на сервере в контексте
  его же REST-запроса, а не получателя рассылки. Фронтенд (`App.jsx`)
  никогда не подставляет эти поля из чужого события напрямую: для уже
  известных задач/досок сохраняется собственное локально известное
  значение, а для по-настоящему новых задач состояние переспрашивается
  отдельным REST-запросом от имени текущей сессии. Иначе читатель,
  увидевший чужое редактирование, мог бы получить в интерфейсе чужую
  роль «владелец» или «редактор».
- Уведомления идут отдельным типом события и не привязаны к тому,
  открыта ли панель уведомлений: счётчик на колокольчике и звук
  (Web Audio API, без бинарного аудиофайла в репозитории) обновляются
  в фоне сразу.
- Переподключение — с экспоненциальной задержкой и случайным джиттером
  (`frontend/src/lib/realtime.js`): при массовом обрыве (например,
  рестарт бэкенда под нагрузкой от многих клиентов) не устраивается
  синхронная атака повторных подключений.

## Модель доступа

Два независимых уровня, оба реализованы через RLS в
`migrations/0002_rls.sql`, а не проверками в коде обработчиков:

- **Доступ к проекту** — роль в `board_members`: `owner` / `editor` /
  `reader`. Читатель видит всю доску, комментирует, отмечает шаги
  чек-листа и загружает файлы, но не создаёт, не двигает и не удаляет
  задачи.
- **Точечный доступ к одной задаче** — запись в `task_grants`
  (`read` / `contribute`) для человека, не состоящего в проекте. Такие
  задачи собираются в разделе «Входящие», где колонки — это
  проекты-источники, а не статусы, и у каждой карточки указан автор —
  кто именно поставил задачу в чужом проекте.

Чек-лист специально разделён на два маршрута: `POST .../steps/:id/toggle`
(отметить выполненным — доступно любому участнику с правом хотя бы
`contribute`) и `PATCH .../steps/:id` (переписать текст — только
редактор задачи). Раньше это был один обработчик, различавший действия
по тому, какие поля пришли в JSON, — источник путаницы, из-за которой
отметка не всегда срабатывала предсказуемо.

Проверить модель доступа:

```bash
make test
```

Восемь проверок: без контекста пользователя не видно ничего; участник
не видит чужой проект; точечный грант открывает ровно одну задачу, а не
всю доску; уровни доступа (`edit`/`contribute`/`read`) действительно
разные; читатель не может править или удалять задачи, но может
комментировать; нельзя записать данные от чужого имени; чужие
уведомления недоступны; хеш пароля не читается напрямую.

## Что стоит доделать перед боевым контуром

- Горизонтальное масштабирование на несколько экземпляров API требует
  вынести `Hub` во внешний pub/sub (Redis или `LISTEN/NOTIFY`) — см.
  раздел про многопоточность выше.
- Файлы хранятся на локальном диске одного инстанса — при нескольких
  экземплярах API нужно S3-совместимое хранилище.
- Нет журнала аудита административных действий (смена ролей, удаление
  проектов) — только activity-лог по задачам.
- `go.sum` не входит в поставку и создаётся локально командой
  `go mod tidy` — в среде сборки этого ответа нет доступа в интернет,
  чтобы зафиксировать точные хеши зависимостей заранее.
